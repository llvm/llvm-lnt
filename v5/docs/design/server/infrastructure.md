# v5 REST API: Infrastructure

This document covers the conventions shared across the v5 REST API: URL
structure, pagination, filtering and sorting, response format, authentication,
and caching. It also covers the routes that sit outside the REST API proper:
the AI orientation document, the health check, the API documentation, and the
crawler policy.

API documentation is generated using the OpenAPI 3.x format, and served
alongside an interactive viewer (see I8).


## I1: URL Structure and Identifiers

**Layout.** `GET /api` is an index that links to the project list and to the API
documentation (see E1). Instance-level routes live under `/api/`
(`/api/projects`, `/api/admin/...`, `/api/auth`). Everything that belongs to a
project lives under `/api/projects/{project}/`, and everything that belongs to a
suite under `/api/projects/{project}/suites/{suite}/` (see D7). Because the
routes of a project or a suite sit one level below its collection, no project or
suite name can collide with a route: a project may legally be named `admin`, and
a suite `schema` or even `suites`. Every path below `/api/projects/` therefore
starts with a project name, and every path below
`/api/projects/{project}/suites/` with a suite name, which is how I5 tells which
project or suite a request addresses.

**No trailing slashes.** No path ends with a `/`. A request that adds one gets a
307 redirect to the canonical form, including for `/healthz`, `/llms.txt` and
`/robots.txt`.
307 is used rather than 301 or 308 so that the method and body are kept, and a
write sent to the wrong spelling is not turned into a GET. The redirect target
is the canonical path with the query string preserved, and no scheme or host,
so that it stays correct behind a TLS-terminating proxy whatever the request
looked like when it reached the server. Client routes are not redirected: the
web UI accepts both spellings itself.

**Identifiers.** Entities are addressed by natural keys (project name, suite
name within its project, machine name, test name, commit value) or by UUIDs
(runs, regressions, regression indicators, profiles), never by internal
auto-increment database IDs. API keys are the one exception: they are addressed
by their `prefix`, which is neither a natural key nor a UUID (see I5). Run and
regression UUIDs may be supplied by the client or generated by the server (see
O1 and E8); all other UUIDs are generated by the server.

In responses, an entity carries its own identifier under the key it is addressed
by: `name` (project, suite, machine, test), `value` (commit), `uuid`, or
`prefix` (API key). I4 covers how one entity refers to another.

**Names in paths.** A server decodes `%2F` to `/` before routing, and removes
`.` and `..` segments. A machine name or commit value that contains a `/`, or
is exactly `.` or `..`, could therefore never be reached by URL -- even the
`Location` header returned when creating it would lead to a 404. A name that
contains a `%` is rejected as well, to avoid any ambiguity with software that
decodes paths. Such names are rejected with 400 wherever they are set: when the
entity is created, including implicitly during run submission (see O1), and
when a machine is renamed (see E2).

Test names and the function names inside a profile are exempt from these rules.
Both legitimately contain `/` or `%` (e.g. a demangled `operator/` overload,
for a function), and arrive implicitly with a run submission, so they never
appear in a path. A request passes a test name in a `test=` query parameter or
in the request body, and a function name in a `function=` query parameter.
Percent-encoding would not help, since `%2F` is decoded before routing.


## I2: Pagination

An endpoint that returns a list of results -- entities, data points or
aggregates -- never returns a bare array. It returns them under `items`, in one
of two envelopes, unless it streams them (see Streaming below):

- Cursor-paginated: `{"items": [...], "cursor": {"next": "...", "previous": null}}`
- Unpaginated: `{"items": [...]}`

The endpoints spec says which envelope each endpoint uses: an endpoint whose
results are bounded -- by the request, by the entity it reads from, or because
there are few of them -- is unpaginated, and the others are cursor-paginated.
`items` is always present, and is an empty list when nothing matches. Even
unpaginated results are wrapped, so that adding pagination to an endpoint later
keeps the shape of its responses.

This applies only to the top level of a response body. An array that is a
field of a larger object keeps its own name (a regression's `indicators`, a
function's `instructions`), and a response that is not a list of results, such
as the lookup table returned by `POST /commits/resolve`, has the shape its
endpoint specifies.

**Cursor pagination** is forward-only. `previous` is always `null` (it is
reserved for future backward pagination) and clients must not rely on it. Cursors are
opaque strings that clients must not parse.

To get the next page, a client sends `cursor.next` back as `cursor`, along with
the same filters and `sort` as the request that returned it: as the `cursor=`
query parameter, or as the `cursor` body key on an endpoint that takes its
filters in the request body (where `limit` is a body key too). Only `limit` may
change from one page to the next. A cursor string that is malformed, or that
is sent with a request for different results than the one it was issued for
(other path parameters, other filters or another ordering), is rejected with
400 `invalid_cursor` rather than answered with a page of the wrong rows.

A cursor may also stop being accepted, with the same error, if the suite's
schema, the server, or an entity named by one of the request's filters changes
between two pages. Whatever the reason, `invalid_cursor` means that the cursor
cannot be used any more, and that the results are available again from the
first page. No other error means this.

Opacity is a contract on the client, not a cryptographic guarantee: a cursor
need not be unforgeable, because it can only point into a query its holder
could have made anyway.

**Page size.** The default page size is 25. Paginated endpoints accept a
`limit` parameter between 1 and `10 000`.

**Streaming.** An endpoint whose results are meant to be read whole, however
many there are, may stream them instead; the endpoints spec says which ones
do. A streaming endpoint returns newline-delimited JSON (`Content-Type:
application/x-ndjson`): one JSON object per line, each line followed by a
newline, with no envelope and no pagination. An empty body means that nothing
matched.

- Errors found before the response starts get their usual status and the
  error envelope (I4).
- Once the response has started, its status cannot change. A failure then
  aborts the response, so that its body is cut short at the transport level
  (with HTTP/1.1, the last chunk is never sent; with HTTP/2, the stream is
  reset), which HTTP clients report as an error. A response that ends normally
  is therefore complete: the HTTP framing says so, not a marker in the body.
- The status and headers are sent before anything is read, and the data is
  sent as it is read rather than at the end, so that a proxy waiting for the
  next bytes does not time out. A compressed response (I4) is compressed as
  it is sent. Like the limit on request bodies (I4), this is a property of
  the deployment: anything it puts in front of the server passes the status,
  headers and data on as they arrive.


## I3: Filtering and Sorting

Filters and sorting are named query parameters. An endpoint that takes its
filters in the request body takes them as keys of the body instead. The
endpoints spec is authoritative for which ones each endpoint accepts, and the
OpenAPI document describes them (see I8).

Common filters include:
- `machine=`, `test=`, `metric=`
- `search=`: case-insensitive text search (see O4)
- `submitted_after=`, `submitted_before=`, `measured_after=`,
  `measured_before=`: exclusive bounds on a run's `submitted_at` and
  `measured_at` (see D5)
- `after_commit=`, `before_commit=`: exclusive bounds on the commit order
- `state=` (for regressions; takes several values)
- `commit=`
- `has_commit=` (for regressions), `has_profiles=` (for commits and runs),
  `has_ordinal=` (for commits and series)
- `tracked=` (boolean, for machines; omitting it returns both)

**Sorting.** `sort=<name>` selects one ordering. Prefix the name with `-` for
descending order (`sort=-submitted_at`). The endpoints spec lists the orderings
each endpoint offers.

**Multiple values.** A query parameter that takes several values is repeated,
once per value (`?state=active&state=detected`).

**Unknown and repeated parameters.** A query parameter that the endpoint does
not accept is rejected with 400 `invalid_request`, and the error names it.
Ignoring it instead would let a typo (`?machnie=linux`) silently widen the
results. A single-valued parameter given more than once (`?limit=1&limit=2`) is
rejected the same way, rather than answered with one of its values. This
applies to every endpoint of the REST API, but not to the routes that I5
exempts from the scope system.

**Names that refer to nothing.** When a filter or request body names something
that does not exist, the result depends on what is named:

| Unknown name | Result |
|--------------|--------|
| A metric | 400 |
| A commit used as a filter (`commit=`) | Empty result |
| A commit used as a range bound | 404, or 400 if the commit exists but has no ordinal |
| Any other entity (a machine, a test, the commit a regression points at) | 404 |

A metric is part of the suite's schema, so naming an unknown one makes the
request invalid. A commit filter selects the rows belonging to that commit, and
a commit that no run has reached yet legitimately has none: a client may well
ask for the runs of a revision before any has been submitted. A range bound names a position in
the commit order, which an unknown commit, or one without an ordinal, does not
have. Every other name is normally taken from what the suite already holds, so
an unknown one is almost always a typo, and is reported rather than answered
with an empty result.

These rules cover names a request uses to refer to something. A schema change
that updates or removes an entry is addressing that entry instead, and returns
404 for an unknown one like any other missing target (see E10).


## I4: Response Format

All REST API responses are JSON, except a successful response from a
streaming endpoint, which is newline-delimited JSON (see I2). A list of results comes in
one of the envelopes from I2; any other response is the entity object itself,
unless its endpoint specifies otherwise. Status codes are limited to 200, 201,
204, 400, 401, 403, 404, 405, 409, 415, and 500.

The routes exempt from the scope system (see I5) are not part of the REST
API and follow their own sections. They serve plain text and HTML as well as
JSON.

The following cases are also outside the REST API, because they are handled
before a request reaches any endpoint:
- An oversized request body is rejected with 413 (see Errors below).
- A request naming a content coding the server does not accept in its
  `Content-Encoding` header is rejected with 415 `unsupported_encoding` (see
  Compression below).
- A trailing slash is redirected with 307 (see I1).
- A URL containing a NUL character is rejected with 400 `invalid_request`,
  since no value the API can act on contains one (see D5).

Each of them is handled the same way whatever credential the request carries.
None of them names a resource, so the reason I5 gives for authorizing before
looking up the resource does not apply.

**Object conventions.** These apply to every response body, so each endpoint's
spec only needs to list its keys.

- A reference to another entity is that entity's identifier (see I1), under a
  key named after the entity (`machine`, `commit`, `test`), not a nested object.
  This keeps items flat and pages small. When the identifier is a UUID, the key
  says so: `run_uuid`. There are three exceptions, specified where they apply: a
  commit's `previous`/`next` neighbours are nested objects; time-series points
  and trend items also carry the commit's `ordinal` and `tag`, because a client
  cannot place a point without them; and an API key's restrictions name a suite
  by its project's name and its own together, in one object (see E11).
- Schema-declared data is always in its own nested dict -- `fields` on machines
  and commits, `metrics` on samples -- never flattened onto the entity.
- A `fields` dict contains every field the suite's schema declares, with `null`
  where the entity has no value. A sample's `metrics` is the exception to this
  rule.
- Values in `fields` and `metrics` use the JSON representation of their
  declared type (see D3) and are never converted to strings. Built-in
  timestamps follow the same convention (see D5).
- Unless specified otherwise, every key an endpoint documents is always
  present, and is `null` when it has no value.

**Errors** all use one envelope, except a failure after a streaming response
has started, which aborts the response instead (see I2):

`{"error": {"code": "not_found", "message": "Machine 'foo' not found in test suite 'llvm/nts'"}}`

`code` is machine-readable and stable. `message` is for humans and may be
reworded at any time, so clients must branch on `code` only and never parse
`message`.

| Code | Status | Meaning |
|------|--------|---------|
| `invalid_request` | 400 | The request is malformed or invalid: bad syntax, a failed validation, an unknown query parameter (see I3), a key the request body does not define, an undeclared `fields` key, an unknown metric name, a missing `?confirm=true` |
| `invalid_cursor` | 400 | The cursor is malformed, was issued for a request for different results, or is no longer accepted (see I2) |
| `unauthorized` | 401 | A credential was required and no usable one was sent, or the `Authorization` header does not hold a usable one (see I5) |
| `forbidden` | 403 | The token is valid, but its scope is insufficient, or it is restricted to other projects or test suites (see I5) |
| `not_found` | 404 | No route matches the path, or an entity named by the path, a filter or the request body does not exist (except where I3 returns an empty result instead) |
| `method_not_allowed` | 405 | The path is an API route, but not for this method. The `Allow` header lists the methods it accepts |
| `duplicate` | 409 | The entity already exists: a run or regression UUID, a project name, a suite name within its project, a schema entry added to a list that already has one of that name |
| `conflict` | 409 | The request contradicts the stored state in a way `duplicate` does not describe, and will fail again if sent unchanged: submitted metadata that disagrees with what is stored (see O2), an ordinal already held by another commit (see O6), the deletion of a project that still has suites (see E13) |
| `retry` | 409 | A concurrent change prevented the request from completing, and nothing was written: the suite's schema changed while the request ran, a schema change, a rename or move of a suite, or a rename, display-name change or deletion of a project could not take its locks in time, or the request and a schema change deadlocked (see D2); or the machine or commit a run submission resolved was deleted before its run was stored (see O8) |
| `unsupported_encoding` | 415 | The request body has a content coding the server does not accept (see Compression below) |
| `internal_error` | 500 | The server failed to process the request |

400 has two codes because `invalid_cursor` calls for a different reaction from
the client: starting again from the first page (see I2). 409 has three codes for
the same reason:

- `duplicate`: the entity is already stored. For a run or regression whose
  UUID the client chose itself, this most likely means that an earlier attempt
  succeeded but its response was lost: the client is done, and must not resend
  under a new UUID, which would store the entity twice.
- `conflict`: the request will keep failing until either the request or the
  stored state changes, so it must not be retried as is. Typically the client's
  view of what is stored -- a machine's metadata, the commit order -- is out of
  date. The `message` says what the conflict is about; the `code` does not,
  because the client's reaction does not depend on it.
- `retry`: nothing was changed, and the failure is not the request's fault, so
  the client may resend it unchanged. The resend is not guaranteed to succeed:
  the concurrent change may have made the request invalid (a metric it names
  was removed, its suite was deleted), in which case the resend gets that
  definitive answer instead.

**HEAD** is answered wherever GET is, on every path: the REST API, the routes
I5 exempts, and the web UI. Per RFC 9110 (section 9.3.2), it gets the status
and header fields a GET would get, errors included, and no body
(`Content-Length` may be omitted). It goes through the same checks as a GET
(I3, I5). A path that does not serve GET does not serve HEAD either.

**Method mismatches** get a 405 only under `/api/`, and its `Allow` header lists
HEAD whenever it lists GET. Elsewhere -- a client route, `/healthz`,
`/llms.txt`, `/robots.txt` -- a method mismatch is a 404 like any other miss.
Whether it is a 405 or a 404, the response does not depend on the credential
the request carries: no endpoint is reached, and which methods a path accepts is
public in the API document (I8, with HEAD implied by GET).

**Oversized request bodies** must be rejected with 413, but they do not have to
use the error envelope: they may be rejected at the transport layer instead.
This is a property of the deployment rather than of any endpoint, so no
endpoint documents it. The limit applies to a compressed body both as sent and
once decoded, and a body is refused once its decoded size exceeds the limit, so
that a small body which expands enormously costs no more than the limit allows.

**Compression.** A request body may be compressed with the gzip content coding,
named in its `Content-Encoding` header (RFC 9110, section 8.4), and the server
must accept it on every request that carries a body. An endpoint sees the body
decoded: whatever the endpoints spec says about a body is about its decoded
form. A request whose `Content-Encoding` header names any other content coding,
or more than one, is rejected with 415 `unsupported_encoding`, and the
response's `Accept-Encoding` header names the codings the server accepts
(RFC 9110, section 15.5.16). A body that does not decode as its coding says --
corrupt, truncated, or followed by data that is not part of it -- is rejected
with 400 `invalid_request`, like a body that is not valid JSON (see I5).

A response may be compressed with a content coding that the request's
`Accept-Encoding` header names (RFC 9110, section 12.5.3). A request without
an `Accept-Encoding` header, or whose header names no coding the server
compresses with, gets an uncompressed response, so a client that does not ask
for compression never has to decode one. A response whose coding depends on
the request's `Accept-Encoding` carries `Vary: Accept-Encoding`.


## I5: Authentication and Authorization

**Scopes.** Every endpoint under `/api/` declares the scope it requires. Scopes
form a strict hierarchy, `read` < `submit` < `triage` < `manage` < `admin`, and
a key grants its own scope plus every lower one: an `admin` key can do
everything a `read` key can. A restricted key grants its scope only on what it
covers (see Restrictions below).

- **read** -- read-only access to test suites and everything in them. Covers
  most GET endpoints, plus read-only POST endpoints such as `commits/resolve`.
- **submit** -- submit runs
  (`POST /api/projects/{project}/suites/{suite}/runs`), create commits
  (`POST /api/projects/{project}/suites/{suite}/commits`)
- **triage** -- create/update/delete regressions, manage regression indicators
- **manage** -- create/update/delete machines; update/delete commits; delete
  runs; create/rename/move/delete test suites and change their schemas;
  create/update/delete projects
- **admin** -- list, create, and revoke API keys

The HTTP method does not determine the scope, in either direction: some POST
endpoints only require `read`, and the API key endpoints require `admin` even
for GET. The `Auth scope` line of each endpoint in the endpoints spec is
authoritative; the list above describes what each scope is for. A client can
find out which scope a token grants, and where, through `GET /api/auth` (see
E12).

**Restrictions.** Every key is either *instance-wide* or *restricted* (see
`restricted` in D5). A restricted key has a list of entries, each a whole
project or a single suite. It *covers* a suite that it lists or whose project it
lists, and it *covers a project in full* when it lists that project. An
instance-wide key covers every project and suite in full.

A request *addresses* a suite when its path is
`/api/projects/{project}/suites/{suite}` or lies under it (see I1): that is
every suite-scoped route, plus E10's routes for one suite. A restricted key
grants its scope only where the table below allows it, and only `read` on any
other request -- exactly what anonymous access gets, so reads are unaffected:

| Operation | What a restricted key needs |
|-----------|-----------------------------|
| A request addressing a suite, other than a move | To cover the suite |
| Moving a suite to another project (E10) | To cover the suite, and the destination project in full |
| Creating a suite in a project (E10), changing a project's display name (E13) | To cover the project in full |
| Creating, renaming or deleting a project (E13) | Nothing it can have: these require an instance-wide key |

Creating, renaming and deleting projects shape the instance rather than the
content of one project, which is why no restricted key can do them. A request is
a move when its body has a `project` other than the path's, and a project rename
when its body has a `name` other than the path's, whether or not that value is
valid. The body is otherwise validated after authorization.

- Only `submit`, `triage` and `manage` keys can be restricted. A restricted
  `read` key would grant nothing more than no key at all, and `admin` keys are
  always instance-wide, since the API key endpoints address no project or suite.
- An entry is linked to its project or suite by identity, not by name (see D5),
  and never changes on a rename or a move: an entry for a suite follows the
  suite. An entry for a project covers the suites that project holds now, so a
  move takes a suite from the keys listing its old project and gives it to those
  listing the new one, which is why moving needs to cover the destination in
  full. A move can leave a key listing a suite along with its new project: both
  entries stay, and the suite's keeps following the suite. A project or a suite
  created later under an old name is not covered.
- Deleting a project or a suite removes it from the keys that list it. A key
  whose last entry is removed stays restricted, to nothing, and grants only
  `read`: it never becomes instance-wide.

This relies on an invariant of every endpoint: a request writes only to what the
table checks -- one that addresses a suite only to that suite, plus the
destination project of a move, and one that creates a suite or changes a
project's display name only to that project.

Coverage is decided when the request is authorized, from the names its path
holds at that moment. If a suite is renamed or moved, or a project renamed,
while a request is being handled, and another suite or project takes the old
name meanwhile, the request may act on it although it was authorized on the old
one. Closing that window is not required: it takes two concurrent changes that
both need `manage`, and lasts no longer than one request.

**Unauthenticated access.** Endpoints that require `read` can be used without a
token. Endpoints that require a higher scope require a valid Bearer token.

**Exempt routes.** The routes that serve documentation, the health check and
the crawler policy are not part of the REST API, and sit outside this section
entirely: `GET /llms.txt` (I6), `GET /healthz` (I7), `GET /api/openapi.json`
(I8), the documentation viewer at `GET /api/docs` (I8), and `GET /robots.txt`
(I10). They do not use scopes or the I4 error envelope, and never
authenticate: an `Authorization` header has no effect on them, not even a
malformed or revoked one, which would be a 401 anywhere else under `/api/`.
Their caching headers still follow I9.

The exemption is an explicit list rather than a consequence of being outside
`/api/`, since two of them are under it. For `/healthz` this matters: its
contract is 200 for healthy and 500 for "cannot reach the database", so a stale
token turning it into a 401 would report a working server as unhealthy. For the
two documentation routes, it keeps a caller with a bad token from being locked
out of the document that explains how to authenticate.

**Presenting a token.** Credentials are sent as `Authorization: Bearer <token>`.
The scheme name is matched case-insensitively, per RFC 9110.

| Request | Result |
|---------|--------|
| No `Authorization` header | Allowed on `read` endpoints; 401 on any endpoint requiring a higher scope |
| Header present, but no usable Bearer credential: unreadable syntax, a scheme other than `Bearer`, or no token after it | 401 on every endpoint under `/api/` |
| A Bearer token that is malformed, unknown, or belongs to a revoked key | 401 on every endpoint under `/api/`, including `read` endpoints that would allow anonymous access |
| A valid token whose scope is insufficient for the endpoint, or that does not grant it on what the request addresses (see Restrictions) | 403 |

A header with no usable Bearer credential is deliberately not treated as an
absent header: falling back to anonymous access would silently ignore a
credential the caller believes it sent. RFC 6750 treats such a request as one
without credentials, which is a 401.

A malformed, unknown or revoked token is a 401 even on `read` endpoints, which
matches RFC 6750's `invalid_token`: it covers malformed tokens as well as
revoked ones. Such a token is never downgraded to anonymous access, which would
turn a broken or revoked token into results the caller mistakes for
authoritative. An insufficient scope matches RFC 6750's `insufficient_scope`.

A 401 carries a `WWW-Authenticate: Bearer` header. Both 401 and 403 use the I4
error envelope, with `code` set to `unauthorized` and `forbidden`
respectively.

**Order of checks.** Authentication comes first, then authorization, then
looking up the resource the request addresses. A request with insufficient scope
therefore gets a 403 whether or not the resource exists: returning 404 first
would let an unauthorized caller find out which resources exist. This matters
for the API keys, the only resources whose existence is not already public, but
the rule applies to every endpoint so that there is only one order to implement
and reason about. It also means that a restricted key gets a 403 for a write to
a suite it does not cover, whether that suite exists or not. A key that lists a
project covers whatever the project holds, so a write to a suite missing from it
is a 404, which tells the caller nothing it could not read anyway.

Some errors may also be returned before authentication: a 400 for a body that
cannot be read at all (a content coding that does not decode, or JSON that does
not parse), and a 400 for a query parameter that I3 rejects. Like the cases I4
handles before reaching an endpoint, none of them depends on whether anything
exists -- which parameters an endpoint accepts is public in the API document
(I8) -- so returning them first reveals nothing.

**Authorization is not cached.** Every authenticated request looks its token up
in the database, so revoking a key takes effect immediately. The lookup reads
small tables that stay in memory; saving that cost is not worth delaying
revocation.

**Tokens.** The server generates each token from a cryptographically secure
random source. A token is exactly 64 lowercase hexadecimal characters (256
bits). The stored `key_hash` is the lowercase hex SHA-256 of the token's ASCII
bytes, and `prefix` is the token's first 8 characters (see D5). A token is
returned exactly once, by the operation that creates it, and cannot be
recovered afterwards: neither the token nor `key_hash` appears in any other
response.

A single SHA-256 is used rather than a password hashing function (bcrypt,
scrypt, argon2). Those exist to make guessing a *low-entropy* secret expensive,
whereas these tokens have 256 bits of entropy -- 224 of them secret, since the
8-character prefix is public -- which puts them far out of guessing range. A
deliberately slow hash would instead let any unauthenticated caller burn server
CPU by sending garbage tokens.

**Creating keys out of band.** Every key-management endpoint requires `admin`
scope, so the API alone cannot create an instance's first key: a new database
has no keys at all, and an operator who revokes the last active `admin` key
has no way to create a replacement. An instance therefore provides an
out-of-band way to create keys, for example a command-line tool run on the
instance. The exact mechanism is implementation-specific.


## I6: AI Agent Orientation

`GET /llms.txt` serves a plain-text orientation document for AI agents,
following the llms.txt convention (analogous to robots.txt).

- Content: what LNT is, its key domain concepts, the API structure, common
  workflows, and links to `/api/docs` and `/api/openapi.json` (see I8).
- Static content outside the REST API: always public, and an `Authorization`
  header has no effect on it (see I5).
- Served as `text/plain` with UTF-8 charset.


## I7: Health Check

`GET /healthz` reports whether the server can serve traffic. It runs a trivial
database query, so a 200 means the process is up *and* can reach PostgreSQL.

- Returns `200 {"ok": true}` on success, and `500 {"ok": false}` if the
  database cannot be reached.
- No authentication: always public, and an `Authorization` header has no effect
  (see I5).
- Deliberately outside `/api/` and not using the I4 error envelope: it is an
  infrastructure probe, not part of the REST API.
- `HEAD /healthz` reports the same status (see I4), for monitors that probe
  with HEAD.


## I8: API Documentation

- `GET /api/openapi.json` serves the OpenAPI 3.x specification of this
  instance's API, as `application/json`. Its `info.title` is `LNT v5` and its
  `info.version` is `5`: the version of the API, which is fixed for the
  lifetime of v5, not the version of the server build.
- The specification describes only responses the API can actually produce. In
  particular, it must not list a status outside the set I4 allows. Frameworks
  commonly document their own validation failure (often 422), which has to be
  corrected to the 400 the error envelope specifies. No operation lists 405,
  since a 405 is returned for a method that has no operation.
- The specification has no HEAD operations: I4 answers HEAD wherever GET is
  answered, so listing it would only repeat every GET operation.
- The specification is written for the API's users. It explains operations,
  parameters and schemas in terms of the API alone, without referring to this
  design documentation or to how the server is built. It opens with the
  conventions every operation shares -- authentication, pagination, filtering
  and errors -- so that it can be read on its own.
- Each operation states the scope it requires (I5), and an operation requiring
  `read` is marked as callable without credentials. An operation requiring
  `submit`, `triage` or `manage` also states what a restricted key needs to call
  it (see I5): to cover the suite, to cover the project in full, to cover the
  suite and the destination project in full (a move), or nothing it can have.
- `GET /api/docs` serves an interactive documentation viewer for that
  specification, as `text/html`.
- How the viewer gets its scripts and stylesheets is up to the implementation.
  It may load them from a third-party CDN rather than from this instance, in
  which case the viewer may only work when the instance is online.
- Both routes are linked from the API index (`GET /api`), under the `openapi`
  and `docs` keys, and from `/llms.txt` (I6).
- Neither requires authentication, and an `Authorization` header has no effect
  on either, even though both are under `/api/` (see I5).
- Swapping the viewer implementation must not change the URL, so the path
  does not name a particular tool.


## I9: Caching

Every response carries a `Cache-Control` header:

| Response | `Cache-Control` |
|----------|-----------------|
| A web UI file | As given in AR2 "Caching" |
| Any other response, to a request with an `Authorization` header (valid or not) | `private, no-store` |
| Any other response, to a request without one | `no-cache, max-age=0` |

The last two also carry `Vary: Authorization`. This way, no cache reuses a
response without checking with the server first, and no shared cache stores a
response that may depend on a credential.


## I10: Crawlers

`GET /robots.txt` serves a robots.txt (RFC 9309) that asks every crawler to
stay away from the whole instance:

```
User-agent: *
Disallow: /
```

It is served as `text/plain` with UTF-8 charset.

Rationale: API responses are computed from the database on request, and I9 require
those responses to not be cached, so crawler traffic hits the database directly.
